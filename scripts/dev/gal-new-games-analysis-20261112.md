## シロクロ：容器与正文的位置已确定

两份索引分别有 1,513 和 3,780 个条目，全部消费到末尾指针之前，没有尾部未解释数据。

每项包含 .NET 7-bit 长度 UTF-8 名、64-bit 偏移/长度、标志及目录串。采到的条目标志均为 `N`。真实路径包括 `/src/game`、`/src/game/add_sys`、`/src/sys`、`/img/bg`、`/img/eventcg`、`/ogg/voice`。

正文分布：主剧情 108 项、追加/系统流程 22 项、引擎系统文本 11 项。之前只有容器头尾，正文位于数百 MB 处，没有实际正文可供适配器读取。现在已知道精确范围，采集不必再上传整个 Unity 数据目录。

与现有 [EdoireTools 的格式说明](https://github.com/crskycode/EdoireTools) 的 `@ARCH000` 特征一致。资源表格式的判断已由本地两份完整索引验证；图像 `.bytes` 的具体包装还需实际条目。

## AI：索引已经解开，尚不能认定剧情语法

参考 [GARbro SakanaGL ArcSX 源码](https://github.com/kyororay/GARbro/blob/master/ArcFormats/SakanaGL/ArcSX.cs) 在本地复现索引解密。索引中的三份存储对应约 41.1 MB、176.9 MB、179.4 MB 的文件；每项保留存储编号、偏移、长度、压缩及加密标志，不能只扫描图片魔数丢掉逻辑名。

条目包括 1,158 个 Ogg、369 个 WebP、127 个 `.sk`、107 个 `.scp`、5 个 `.ks`，其余为 UI/配置/字体等。本地已有头尾区间包含 549 个完整条目，均已按相应加密/压缩标志处理；图片/音频有可识别文件头，部分脚本为 `FA FA` 开头的词元及字符串表，并非普通 UTF-8 文本。

剧情为：

- `scenario/define.ks`
- `scenario/ep_all.ks`
- `scenario/epend.ks`
- `scenario/main.ks`
- `scenario/start.ks`

它们位于 `aiduma-001-0.sxstorage` 约 40.3 MB 的区段，现有头尾不覆盖。`ep_all.ks` 存储长度 112,342 字节。下一轮只取这些条目和 `src/` 项目脚本、配置，共 206,768 字节，不重收 DLL/EXE。

本地使用 Node 内置 Zstd，没有安装 GARbro、Python 解包库或游戏运行时。正式接入时仍需验证实际镜像 Node 接口，并保留解压大小上限。

## ツヴァイ：已从“缺密钥”推进到“验证剧情格式”

采用 [xp3-brute 的静态恢复算法及公开合成测试向量](https://github.com/xmoezzz/xp3-brute/blob/master/src/krkr_exe.rs)，从本作原始 EXE 解析 PE 资源。未运行 EXE/DLL。

依次验证了：

1. 本地 KDF 实现与公开合成向量一致。
2. 解出的 STARTUP.TJS 具有有效 TJS2100 结构，能读出字符串池。
3. BOOTSTRAP 解密、zlib 长度及 PE 头匹配，PARAMS 的排列有效。
4. 本作派生密钥通过 data/bgimage/evimage/fgimage/voice 五份特殊索引的认证。
5. 现有 app HXV4 模块直接解密已采区间：data 8 项、bgimage 3 项、fgimage 27 项、voice 3 项，共 41 项 adlr 匹配。evimage 只有部分文件头可采，已解出 PNG 头，不能冒充完整文件校验通过。

每包第 0 项都是未加密的警告文本，声明长度/校验和与实际段不一致；它与上述受保护的真实资源分开统计，不把它作为“本作密钥错误”的证据。

已看到 TJS 配置文本、普通 PNG、TLG5、Ogg，以及 `TJS/4s0` 序列化条目。**还没有完整剧情样本**，所以不能断言本作的场景就是现有适配器要求的 PSB `name/scenes/texts` 结构。

下一轮按 data/patch 索引读取受保护条目的小段头及 24 个均匀完整样本。头段明确标记 partial，先识别正文类型；不把截断数据交给正式导入。
